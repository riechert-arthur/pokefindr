# Internationalization

How PokeFindr shows its copy in more than one language. Decided in #176 (R9).

## Decisions

### Library: next-intl

[next-intl](https://next-intl.dev) works with the App Router and Server Components
(`getTranslations` on the server, `useTranslations` on the client), formats messages as ICU
(plurals, selects, numbers, dates), types message keys, and doesn't care what format the
messages are stored in.

### Messages: one YAML file per language, built to JSON

`messages/en.yml` is the source catalog, nested by area (`map.status.inView`,
`auth.login.title`). Other languages (`messages/es.yml`) have the same keys. YAML comments next
to a message give translators the context: where it shows and what the placeholders hold.

`npm run i18n:build` turns each YAML file into JSON in `src/i18n/generated/` (not committed),
and the app, Storybook and tests import the JSON. It runs on `npm install`, and again whenever
`next dev`, `next build`, Storybook or Vitest start; `next dev` also rebuilds when a YAML file
changes. Key types come from the English JSON, so a typo in a key fails typecheck.

The other option was a webpack/Turbopack loader that imports `.yml` directly. It needs separate
setup for Next, Vite (Storybook) and Vitest, and the key types still need a generated file. A
build step does the same everywhere.

### Routing: English without a prefix, other languages with one

English stays where it is (`/map`); Spanish is at `/es/map` (next-intl's
`localePrefix: "as-needed"`). Every language has its own URL, so links stay shareable and search
engines can index each one. Pages move under `src/app/[locale]/`; API routes, `/.well-known`
and the generated icons stay outside it.

The alternative was one set of URLs, with the language from a cookie or the profile only. It's
simpler, but a language has no URL of its own for search engines or for sharing.

### Middleware: one function, auth inside next-intl's

`src/middleware.ts` runs on every page and on the API routes that need a session:

1. API routes only check the session, as before.
2. For pages, the session check runs first on the signed-in pages (`/home`, `/settings`,
   `/admin`, with or without a language prefix). A visitor without a session goes to the login
   page in their language.
3. Then next-intl's middleware picks the language and rewrites `/map` to `/en/map`. It passes
   the request's headers on, including the verified `x-user-id`.

Every other page has any `x-user-id` and `x-user-tier` a client sent removed, so only the
middleware can set them.

### Picking the language

The language in the URL wins. On a page without a prefix, the saved choice (the `NEXT_LOCALE`
cookie) comes next, then the browser's `Accept-Language`, then English. A signed-in user's
choice is also saved to their profile, which sets the cookie when they sign in on another device
(#182).

### Scope

Translated: UI copy, page metadata, emails and the messages users see from the API, and map
labels. Not translated: blog posts (content, translated separately if ever), the privacy policy
and terms (English only unless legal review says otherwise), the admin pages (staff only), and
logs.

### Releasing a language

A language is listed in `LOCALES` (`src/i18n/routing.ts`) once its URLs exist, and in
`PUBLIC_LOCALES` once it's ready for visitors. Only public languages are detected from
`Accept-Language`, offered in the switcher, listed in the sitemap and hreflang, and indexed.
Spanish goes public in #186, after a fluent speaker reviews it.
