# Internationalization

How PokeFindr shows its copy in more than one language. Decided in #176 (R9).

## Decisions

### Library: next-intl

[next-intl](https://next-intl.dev) works with the App Router and Server Components
(`getTranslations` on the server, `useTranslations` on the client), formats messages as ICU
(plurals, selects, numbers, dates), types message keys, and doesn't care what format the
messages are stored in.

### Messages: one YAML file per language, built to JSON

`messages/en.yml` is the source catalog, nested by area (`map.status.inView`,
`auth.login.title`). Other languages (`messages/es.yml`) have the same keys. YAML comments next
to a message give translators the context: where it shows and what the placeholders hold.

A test in CI checks that every catalog has the same keys as English and the same placeholders in
each message (#178). If a message is still missing at runtime, the English one shows instead of
the raw key.

`npm run i18n:build` turns each YAML file into JSON in `src/i18n/generated/` (not committed),
and the app, Storybook and tests import the JSON. It runs on `npm install`, and again whenever
`next dev`, `next build`, Storybook or Vitest start; under `next dev`, `next.config.ts` also
watches `messages/` and rebuilds on every change. Key types come from the English JSON, so a typo
in a key fails typecheck. `npm run typecheck` and `npm run lint` build it first too, so they work
after an install that skipped scripts. The `yaml` parser is a regular dependency, because
installs without dev dependencies still run the build.

The other option was a webpack/Turbopack loader that imports `.yml` directly. It needs separate
setup for Next, Vite (Storybook) and Vitest, and the key types still need a generated file. A
build step does the same everywhere.

### Routing: English without a prefix, other languages with one

English stays where it is (`/map`); Spanish is at `/es/map` (next-intl's
`localePrefix: "as-needed"`). Every language has its own URL, so links stay shareable and search
engines can index each one. Pages move under `src/app/[locale]/`; API routes, `/.well-known`
and the generated icons stay outside it.

Pages that stay in English (blog posts, the privacy policy and terms) also have a Spanish URL, so
the app around them (navigation, footer) is in the visitor's language. Their canonical URL is the
English one, and they're left out of hreflang and the sitemap in other languages, so search
engines don't index them twice (#183).

The alternative was one set of URLs, with the language from a cookie or the profile only. It's
simpler, but a language has no URL of its own for search engines or for sharing.

### Middleware: one function, auth inside next-intl's

`src/middleware.ts` runs on every page and on the API routes that need a session:

1. API routes only check the session, as before. Any route handler that reads `x-user-id` or
   `x-user-tier` has to be in the matcher: a route outside it gets whatever headers the client
   sent.
2. For pages, the session check runs first on the signed-in pages (`/home`, `/settings`,
   `/admin`). It matches the path after the language prefix and after decoding it, as next-intl
   does, so `/%68ome` is checked like `/home`. A visitor without a session goes to the login page
   with the URL's prefix (`/es/home` → `/es/login`); an unprefixed `/login` then gets its
   language like any other page.
3. Then next-intl's middleware picks the language and rewrites `/map` to `/en/map`. The verified
   headers only reach the page if they're on the request next-intl is given:
   `intl(new NextRequest(req, { headers }))`. Editing a copy of the headers does nothing.

Every other page has any `x-user-id` and `x-user-tier` a client sent removed, so only the
middleware can set them.

### Picking the language

A prefixed URL (`/es/map`) is always in its language. A URL without a prefix is English unless
the visitor has picked or visited another language: then the saved choice (the `NEXT_LOCALE`
cookie) comes first, then the browser's `Accept-Language`, then English, and next-intl redirects
to the prefixed URL. So a shared `/map` link opens in the visitor's own language. Picking English
in the switcher rewrites the cookie as it navigates (next-intl's router does this), so English
stays picked.

The cookie is kept for a year, but only once more than one language is public: until then
next-intl neither reads nor writes it, so nothing is saved while English is the only choice. A
signed-in user's choice is also saved to `profiles.locale` (migration 0019), and only a public
language can be saved. Logging in sets the cookie from it and opens the next page in that
language, so it follows them to another device; logging out clears the cookie, so a shared
computer goes back to the browser's language (#182).

The switcher (`LanguageSwitcher`) is in settings, the footer and the app rail. It lists the
public languages in their own names and hides while there's only one.

Emails and API errors have no URL to go by. They use the profile's language, then the request's
(the page it came from, then the cookie), then English (#185). Someone who signs up keeps the
language they signed up in.

### Scope

Translated: UI copy, page metadata, emails and the messages users see from the API, and map
labels. Not translated: blog posts (content, translated separately if ever), the privacy policy
and terms (English only unless legal review says otherwise), the admin pages (staff only), and
logs.

### Releasing a language

A language is listed in `LOCALES` (`src/i18n/routing.ts`) once its URLs exist, and in
`PUBLIC_LOCALES` once it's ready for visitors. Only public languages are detected from
`Accept-Language`, offered in the switcher, listed in the sitemap and hreflang, and indexed.
Detection only ever picks a public language: the middleware drops the others from
`Accept-Language` and ignores a cookie naming one, so a language that's only in `LOCALES` is
reachable by its URL alone. Prefixed pages of a language that isn't public are `noindex`.
English and Spanish are public (#186).

## Working with messages

### Adding copy

1. Add the message to `messages/en.yml` under its area, with a comment if where it shows or
   what a placeholder holds isn't obvious from the key.
2. Add it to every other catalog (`messages/es.yml`) too. CI checks that each catalog has the
   same keys (#178).
3. Read it with `useTranslations("area")` in a component (server or client), or
   `await getTranslations("area")` in an async Server Component, `generateMetadata` or a route
   handler.

```tsx
const t = useTranslations("errors.notFound")
return <h1>{t("title")}</h1>
```

Plurals and numbers go in the message, not the code:

```yaml
count: "{count, plural, one {# place} other {# places}}"
```

### Numbers, dates and distances

- `useFormat()` (`src/i18n/format.ts`) has counts (`count`, `kindCount`, `places`), event dates
  (`eventWhen`) and `ago`, all in the page's language. Tests get the same functions from
  `formatFor(locale)` in the test helper.
- `useDistance()` (`src/i18n/useDistance.ts`) writes distances and radii in miles or kilometers.
  The unit comes from the browser's region (`es-MX` → km); a language without one, like the
  site's `en` and `es`, gets miles, since the map is of the US. The server renders miles and
  the browser switches after hydration. Distances and radii are stored in miles everywhere.
- Don't write `n === 1 ? … : …`: put the plural in the message.

### Links and redirects

Import `Link`, `redirect`, `useRouter` and `usePathname` from `@/i18n/navigation`, not from
`next/link` or `next/navigation` (lint enforces it). They keep the current language:
`<Link href="/map">` goes to `/es/map` on a Spanish page, and `usePathname()` returns `/map`.
An API route has no language, so links to one stay plain.

### Static pages

A Server Component page or layout that should be built ahead of time calls
`await setPageLocale(params)` (`src/i18n/static.ts`) first. Without it, next-intl reads the
language from the request headers, which makes the page dynamic.

### Checks in CI

- `__tests__/i18n/catalogs.test.ts`: every catalog has exactly English's keys, every message
  parses as ICU with the same placeholders and tags as English, and every English message is read
  somewhere in `src/`. A key built from parts (`kinds.${kind}.name`) counts, and so does one
  read through a variable (`t(failure)`) when its last part appears as a string in `src/`.
- Lint flags words in JSX text, in the attributes people read or hear (`aria-label`, `title`,
  `placeholder`, `alt`, `label`) and in `toast(...)` in `src/app` and `src/components`. The
  admin pages and the privacy policy and terms are exempt (English only). For text that really
  isn't copy, like the logo's wordmark, disable the rule on those lines with a comment saying why.

### Map labels

The basemap's place names follow the page's language: `useLocalizedLabels` (in
`BasemapOverlays.tsx`) sets every name label's `text-field` to the tiles' `name:<lang>`, then
`name:latin`, then `name`, and again whenever the theme loads a new style. Our own names come
from the catalog (`states`) or the browser (`countryName`, from `Intl.DisplayNames`).

### Search engines and link previews

- Indexable pages build their metadata with `pageMetadata(path, locale, {...})`
  (`src/i18n/seo.ts`): the canonical URL, hreflang for each public language with English as
  `x-default`, `og:locale`, and the link preview in the page's language (`/social-card`,
  `/es/social-card`). Next replaces a layout's `openGraph` whole when a page sets one, which is
  why these go through the helper. Content that's English everywhere (blog posts, legal pages)
  uses `englishOnlyMetadata`, so the English page is canonical.
- `/sitemap.xml` lists `INDEXED_PAGES` and the blog posts in each public language. Add a page there
  when it should be indexed. The signed-in pages, admin and login callbacks stay out.

### Emails and API errors

- Emails (`src/server/email/templates.ts`) read the `email` messages in the recipient's language:
  `profiles.locale`, or for a new sign-up the page they signed up on. API routes have no language
  of their own; `requestLocale` (`src/server/i18n.ts`) reads it from the page that made the request
  (the Referer's prefix), and `identityRequest` passes it to Better Auth's email hooks. Sign-up
  saves it on the new profile.
- An API error a page shows is `apiError(code, english, status)` (`src/server/api-error.ts`): the
  English `error` for anyone reading the API, and a `code` the page turns into the catalog's
  `apiErrors` message with `useApiError()` (or `useSubmitError()` for a toast). Admin routes, job
  output and logs stay in English.

### Translating

1. **Draft.** When English changes, CI fails until every catalog has the same keys
   (`__tests__/i18n/catalogs.test.ts`). Draft the missing messages; Claude can do this from
   `messages/en.yml`, whose comments say where each message shows and what its placeholders hold.
   Keep the placeholders, tags and ICU structure exactly; plurals use the target language's
   forms (`one` and `other` in Spanish).
2. **Terms.** Use the catalog's existing words: in Spanish, "máquina expendedora", "tienda de
   cartas", "evento", "iniciar sesión", "tú". Brand names (PokeFindr, Pokémon, TCG, Discord,
   Claude) stay as they are.
3. **Review.** A fluent speaker reads the change before release: in the PR diff, and on the pages
   at 390px and 1280px wide, since translations run longer (Spanish about 25%). Storybook's
   Language toolbar shows each component in the language.
4. **Check.** CI runs the catalog checks, the copy lint rule and the accessibility checks, which
   test every story in each language (`.storybook/test-runner.ts`).

A new language: add `messages/<code>.yml`, add the code to `LOCALES` (its pages are reachable at
`/<code>`, not indexed, not detected), translate and review it, then add it to `PUBLIC_LOCALES`
along with its `og:locale` in `src/i18n/seo.ts`.

### Tests and stories

- Component tests import `render` from `__tests__/helpers/intl` instead of
  `@testing-library/react`. It wraps the tree in the provider with the English messages, or
  another language with `render(ui, { locale: "es" })`. `message()("area.key")` returns a
  message, to assert on the catalog instead of a copy of the English.
- Storybook has a Language toolbar next to the theme.
